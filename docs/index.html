Knowledge Transfer Document

Kinova Gen2 ROS 2 Port

This document serves as a knowledge transfer artifact detailing the migration of the kinova-ros package (originally written for ROS 1) to ROS 2 (Humble). Porting legacy robotics drivers and simulation environments involves bridging gaps between old build systems (catkin to ament), updated physics engines (Gazebo Classic to Ignition/Gazebo), and entirely rewritten motion planning frameworks (MoveIt to MoveIt 2).

0. Hardware Deployment

To launch the physical Kinova Gen2 arm in the ROS 2 environment, follow this sequence:

0.1 Launch the Driver

The driver handles communication with the arm via USB or Ethernet.

ros2 launch kinova_bringup kinova_robot_launch.py kinova_robotType:=j2s6s200

0.2 Launch MoveIt 2 & Perception

This brings up the planning scene, RViz visualization, and the RealSense depth camera.

ros2 launch kinova_bringup sample.launch.py

1. Hand-Eye Calibration (Extremely Important)

Accuracy in 3D clicking and autonomous scooping depends entirely on the quality of the calibration between the camera and the robot's end-effector.

1.1 Calibration Tools

You can use either of the following tools integrated into this port:

  • easy_handeye2: Recommended for a straightforward GUI-based workflow.
  • MoveIt Calibration: Integrated into MoveIt 2, useful if you want to use MoveIt's internal solvers.
ros2 launch kinova_bringup easy_handeye.launch.py

1.2 Physical Stability

Hardware Warning

Ensure the depth camera (RealSense) is securely mounted to the end-effector. Even a tiny shake or "wobble" due to a missing screw will invalidate the calibration transform. If the camera moves by 1mm, your 3D target will be off by several centimeters at distance.

1.3 Calibration Target Selection

Prefer ArUco boards over ChArUco boards for this specific arm. ChArUco boards can sometimes suffer from corner detection ambiguity at high angles with this camera's resolution.

Printing Instructions:

  • Scale: When printing the board, do NOT use "Fit to page". Use 100% scale (Precise Printing).
  • Measurement: Regardless of your print settings, use a high-precision ruler to measure the actual black border of the marker on paper.
  • Manual Entry: Enter this measured value (in meters) manually into the calibration GUI. Do not trust the default values in the scripts.

1.4 Sampling Strategy ($AX = XB$)

Solving the hand-eye equation ($AX = XB$) requires high diversity in the samples taken.

  • Take at least 20 samples: Do not stop early.
  • Diversity: Rotate the gripper significantly between samples. Move it to the edges of the camera's FOV.
  • Don't trust early results: Even if you get a very low reprojection error for the first 3 samples, continue to 20+. Early low errors are often mathematical "lucky guesses" that will fail when the arm moves to a different quadrant.

2. Intrinsic Camera Calibration

While the RealSense driver provides factory intrinsics via the camera_info topic, these are "mostly correct" but may require custom calibration for high-precision tasks.

2.1 Using Factory Intrinsics

The point_selector_node automatically listens to the /camera/camera/color/camera_info topic. It extracts the focal lengths (fx, fy) and optical centers (cx, cy) to project 2D clicks into 3D space.

Verification

Always check the node logs on startup to ensure the values match your expectations:

[point_selector_node]: Camera intrinsics received: fx=615.4, fy=615.8

2.2 Custom Checkerboard Calibration

If you notice a systematic "shift" in your 3D points (especially towards the edges of the image), the factory intrinsics may be slightly off due to lens wear or temperature changes.

When to recalibrate:

  • 3D points are accurate in the center but drift at the corners.
  • The camera has been dropped or subject to vibration.
  • You are using a non-standard resolution.

Tools: Use the standard camera_calibration tool from the ROS 2 image pipeline:

ros2 run camera_calibration cameracalibrator --size 8x6 --square 0.024 --ros-args -r image:=/camera/camera/color/image_raw

After calibration, the new parameters should be uploaded to the RealSense hardware using the realsense-viewer tool or saved into a local camera_info YAML file for the driver to load.

3. Build Errors & Missing Files

3.1 Missing Vendor Binary Blobs (.so files)

Error Output

CMake Error at cmake_install.cmake:46 (file):
file INSTALL cannot find
"/home/user/workspace/src/kinova-ros2/kinova_driver/lib/x86_64-linux-gnu/USBCommLayerUbuntu.so":
No such file or directory.

The Mistake: The Kinova ROS 1 driver relies on proprietary, pre-compiled C++ binaries provided by Kinova (e.g., USBCommLayerUbuntu.so). When transferring the source code to a new ROS 2 workspace, these binary folders (i386-linux-gnu and x86_64-linux-gnu) were not tracked by git or were accidentally omitted from the lib folder.

The Solution

Locate the original binary blobs from the vendor SDK or the old ROS 1 workspace and copy them into the correct directory structure before building.

cp -r /old_workspace/src/kinova-ros/kinova_driver/lib/* src/kinova-ros2/kinova_driver/lib/

Ensure CMakeLists.txt uses the install(FILES ...) directive to copy these into the ROS 2 install/lib directory.

4. Gazebo Simulation Issues

4.1 Meshes Failing to Load in Gazebo (Invisible Robot)

Error Output

[GUI] [Err] [SystemPaths.cc:474] Could not resolve file [model://kinova_description/meshes/wrist_spherical_1.STL]
[GUI] [Err] [SceneManager.cc:404] Failed to load geometry for visual

The Mistake: In ROS 1 + Gazebo Classic, the package:// or model:// URIs resolved magically via the ROS_PACKAGE_PATH. In ROS 2 + Ignition/New Gazebo, the physics engine operates independently of ROS packages unless explicitly told where to look. The launch files did not export the correct resource paths.

The Solution

Pass the explicit ROS 2 share directory paths to Gazebo using environment variables within the Python Launch file. Both IGN_GAZEBO_RESOURCE_PATH and GZ_SIM_RESOURCE_PATH must be set.

pkg_share_path = os.path.dirname(get_package_share_directory('kinova_description'))
gazebo = ExecuteProcess(
    cmd=['ign', 'gazebo', '-r', world_file],
    additional_env={
        'IGN_GAZEBO_RESOURCE_PATH': pkg_share_path + ':/opt/ros/humble/share',
        'GZ_SIM_RESOURCE_PATH': pkg_share_path + ':/opt/ros/humble/share',
    }
)

4.2 Controller Manager Fails to Start

Error Output

[spawner] [WARN]: Could not contact service /controller_manager/list_controllers
[spawner] [INFO]: waiting for service /controller_manager/list_controllers to become available...

The Mistake: This happens when the ros_gz_sim spawner node attempts to inject the URDF into the simulation, but it spawns the robot into the wrong "world" internally, or the URDF lacks the gz_ros2_control plugin. If the robot isn't spawned, the simulated controller manager is never instantiated.

The Solution

Add the -world argument to the ros_gz_sim create node, ensuring it targets the exact name defined inside the .sdf file (e.g., <world name="point_goal_scene">).

5. MoveIt 2 & Planning

5.1 Pilz Planner Missing Cartesian Limits

Error Output

[move_group]: Parameter 'robot_description_planning.cartesian_limits.max_trans_vel', is not set in the config file.

The Mistake: MoveIt 2 introduces the Pilz Industrial Motion Planner for deterministic Cartesian movements (LIN, PTP, CIRC). Unlike the default OMPL planner, Pilz strictly requires Cartesian velocity and acceleration limits to be defined. The ported ROS 1 joint_limits.yaml only contained angular limits.

The Solution

Append a cartesian_limits block to the end of your joint_limits.yaml file.

cartesian_limits:
  max_trans_vel: 0.1
  max_trans_acc: 0.1
  max_trans_dec: 0.1
  max_rot_vel: 0.1

6. Kinova API Error Codes

When working with hardware, the Kinova API may return specific numeric error codes. Below are the most common ones encountered during development:

Code Meaning Common Root Cause
1015 Device Not Found Loose USB/Ethernet cable, insufficient power supply to the arm, or USB passthrough issues in Virtual Machines.
1001 RS485 Error Internal communication failure between joints. Often requires a power cycle.
1014 Init Connection Error The API failed to initialize the communication layer. Check udev rules.

7. File Manifest & Logic Meanings

The root directory contains several utility and orchestration scripts. Here is what they do:

  • robot.py: The core orchestrator. Contains the FeedingOrchestrator class which manages the state machine for the entire scooping cycle.
  • run_scoop.py: The main entry point for the feeding task. It uses the joint sequences defined at the top of the file to move between pre_scoop, scoop, and feed.
  • food_segmenter.py: Uses OpenCV to isolate food in the camera feed. Mistakes here usually involve incorrect HSV color bounds for the food being used.
  • click_pointer.py: Translates a 2D pixel click from the user into a 3D goal point in the robot's base frame (root).
  • record.py: A utility script to save the robot's current joint states into a YAML file for later playback.
  • *.yaml: These files (e.g., working_joints.yaml) store precise joint positions that have been verified to work on the hardware.

8. Runtime Stability & Hangs

8.1 Python Nodes Exiting Silently / GUI Freezing

Symptom

Nodes like point_selector_node exit with process has finished cleanly immediately on boot, or the Ubuntu desktop prompts to "Wait / Force Quit" the Gazebo application.

The Mistake: 1. Silent Exits: The node relied on OpenCV (cv2.namedWindow) to render a UI. In headless environments or environments with X11 forwarding issues, OpenCV throws a fatal exception. Because it wasn't caught, the node died silently.
2. GUI Hangs: The Gazebo .sdf file was running the ODE physics engine with a max_step_size of 0.005 and an update rate of 200Hz. This maxed out the CPU threads on standard hardware, starving the GUI thread.

The Solution

Fixing Silent Exits: Wrap OpenCV initialization in a try/except block and implement a "headless mode" fallback. Add traceback.print_exc() to the main loop to ensure fatal errors are always logged.

Fixing Physics Overload: Edit the .sdf world file to reduce the physics load:

<physics name="default_physics" default="true" type="ode">
  <max_step_size>0.01</max_step_size>
  <real_time_update_rate>100</real_time_update_rate>
</physics>

9. Legacy C++ Warnings & Bugs

9.1 Compilation Warnings Treated as Errors

Error Output

warning: unused parameter ‘result’ [-Wunused-parameter]
warning: ‘bool setsEqual(const std::vector<std::string>&, ...)’ defined but not used

The Mistake: The ROS 2 `ament_cmake` environment enforces strict compiler flags (often treating warnings as errors) to enforce modern C++ standards. Legacy ROS 1 code frequently left helper functions unused or ignored actionlib callback parameters.

The Solution

Explicitly cast unused parameters to void to silence the warning, or simply remove unused helper functions from the source files.

void result_callback(const WrappedResult & result) {
    (void)result; // Silences the unused parameter warning
    is_client_active = false;
}

9.2 Logical Bug: Assignment in Conditional

Error Output

warning: suggest parentheses around assignment used as truth value [-Wparentheses]
if(mouse_was_up=true)

The Mistake: A classic C++ typo in kinova_interactive_control.cpp. Using a single equals sign = performs an assignment instead of a comparison ==. This means the condition always evaluates to true, overriding the intended state machine logic.

The Solution

Change the assignment to an evaluation of the boolean variable itself.

// Old: if(mouse_was_up=true)
// New:
if(mouse_was_up) {
    // Execute state logic...
}
